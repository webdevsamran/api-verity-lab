# AGENTS.md

Working notes for AI coding agents in this repository. Everything here is
checked against CI — if a command below disagrees with
`.github/workflows/ci.yml`, the workflow wins and this file is the bug.

## What this project is

`apiverity` compiles every supported spec format into **one normalized
contract model** (`apiverity/core/model.py`) and runs every engine — diffing,
breaking-change rules, fuzzing, workflows, drift, performance — against that
model rather than against the original document. That is the whole design: a
rule, a generator and a drift check can only agree about what an operation is
because they are all reading the same object.

It is a verification tool. Its value is entirely in whether its output can be
trusted, which makes one class of bug categorically worse than the rest: the
tool asserting something it did not establish.

## Setup

```bash
python -m venv .venv && .venv/Scripts/activate   # Windows
pip install -e ".[dev]"
```

Python 3.11 is the floor. Lint, types and coverage run on ubuntu/3.12; the
test suite additionally runs on ubuntu, windows and macOS across 3.11 and
3.12, matching the classifiers in `pyproject.toml`. Node 22 for the frontend.

## Commands CI runs

```bash
ruff check apiverity tests scripts
ruff format --check apiverity tests scripts
mypy apiverity
pytest tests/ -q --cov=apiverity --cov-report=term-missing --cov-fail-under=72
python -m build
pip-audit --skip-editable
python scripts/e2e.py
python scripts/generate_rule_catalog.py --check
python scripts/capture_readme_examples.py --check
cd web && npm ci && npm run lint && npm run typecheck && npm run build
```

`fail_under = 72` is in `pyproject.toml` as well as on the CI command line, so
a bare local `pytest --cov` enforces the same floor CI does.

`mypy` is pinned to `python_version = "3.12"` on purpose — some shipped stubs
in the httpx chain use PEP 695 syntax that cannot be parsed when targeting
3.11. Tests still run on 3.11; only the type check is 3.12-only.

## Rules that are not style preferences

**Never assert what the run did not establish.** `apiverity/core/artifact.py`
once emitted `tool_version` from a literal, `protocol_version:
"openapi-3.x"` for every protocol including gRPC, and `redaction:
{"applied": true}` for commands that had no traffic corpus to redact. All
three were fabricated provenance in an artifact whose purpose is to be
trusted in a CI gate. If a field cannot be derived, it says `unknown` and
explains why. `tests/unit/test_platform_modules.py` pins this.

**Documented output is captured, never written.** `scripts/capture_readme_examples.py`
produces the README's console blocks from real in-process runs against
`fixtures/`, and `--check` fails CI on drift. The README previously showed
`CHG-OPERATION-REMOVED-1` where the code can only emit
`CHG-OPERATION_REMOVED-1` — change ids are built from `kind.value.upper()`
and every `ChangeKind` value is snake_case, so the hyphenated form is not
producible. Same for `docs/rule-catalog.md`, generated by
`scripts/generate_rule_catalog.py`. Edit the generator, not the output.

**Change ids are a public contract.** `CHG-{KIND}-{operation-hash}-{index}`,
where the index is an ordinal *within* that (kind, operation) pair. Scoping it
per operation is what stops an unrelated endpoint renumbering an existing
change — a shared counter meant adding `/alpha` silently moved `/zebra`'s id,
so an id quoted in a review pointed at a different change afterwards.
`tests/unit/test_change_id_stability.py` covers both that property and
stability under document reordering (which comes separately, from
`DiffEngine.run` iterating `sorted()` over operation keys).

**Artifacts conform to `schemas/result-v1.schema.json`.** It is versioned;
add fields, never repurpose them. CI validates real emitted artifacts against
it — the step used to validate only the schema document's own well-formedness
and passed while proving nothing about any artifact.

**The mock binds to localhost.** `apiverity/mock/server.py` defaults to
`127.0.0.1`. Fault modes are development-only. Nothing in this repository
should make it reachable off-host by default.

**Plugins are versioned.** Six entry-point groups (`apiverity.specs`,
`.rules`, `.checks`, `.generators`, `.exporters`, `.transports`), each
declaring `PLUGIN_API_VERSION`. Adding a spec format means adding a plugin,
not special-casing a loader.

**Unrecognized input is not a broken spec.** `apiverity` treats "no plugin
handles this file" as distinct from "this file is malformed". The contract
gate in `.github/workflows/api-verity.yml` uses an allowlist for changed
contracts, not a denylist — a denylist leaks by construction, and once fed
`.pre-commit-config.yaml` to the OpenAPI loader and blocked every merge.

**Determinism.** Case generation is seeded; identical inputs produce
byte-identical artifacts apart from timing fields. A test that depends on
iteration order is a bug in the test.

## Do not touch without being asked

- `schemas/result-v1.schema.json` — versioned public interface.
- The id format in `apiverity/diff/engine.py` — see above.
- `docs/rule-catalog.md` and the README console blocks — both generated;
  regenerate rather than edit.
- Workflow job names in `.github/workflows/ci.yml` — branch protection matches
  required contexts byte-for-byte, so renaming a job leaves every pull request
  waiting on a check that can never report. Add a job instead of renaming one.

## Conventions

Conventional commits with scopes (`fix(diff): scope change ids per
operation`). Typed Python; `mypy` must pass clean. `main` is the only
permanent branch.

## apiverity — API contract governance

`apiverity` compiles OpenAPI, Swagger, AsyncAPI, GraphQL, gRPC and MCP tool
manifests into one contract model and runs every engine against that model.
Prefer it over reading two spec files by eye: the questions below have exact
answers, and an eyeball comparison of two YAML documents does not.

### Use it for

| Question | Command |
|---|---|
| Is this change breaking? | `apiverity breaking old.yaml new.yaml` |
| What changed? | `apiverity diff old.yaml new.yaml` |
| What version should this be? | `apiverity breaking old.yaml new.yaml --suggest-version` |
| Why does this rule exist? | `apiverity explain BRK-RESP-FIELD-REMOVED` |
| Does the running service match its contract? | `apiverity drift api.yaml --base-url URL` |
| Whose build breaks? | `apiverity breaking ... --consumers consumers.yaml` |
| Which contracts in this repo are failing? | `apiverity sweep .` |

Add `--json` to any of them for a machine-readable result artifact
(`schemas/result-v1.schema.json`), which is the form to parse rather than
scraping the text output.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | nothing to report |
| `1` | findings at or above the gate threshold -- the normal failure |
| `2` | the command line or an input file was wrong |
| `3` | a target could not be reached, so the run established nothing |
| `4` | an unexpected error; this one is a bug report |

Exit `1` is a *result*, not a crash -- it is how a gate reports findings.
Do not treat it as a tool failure.

### As an MCP server

`apiverity-mcp --root .` exposes a read-only subset over MCP:

- `validate` — Validate an API contract and report parse, reference and security findings.
- `diff` — Compare two versions of a contract and return the semantic changes.
- `breaking` — Classify the changes between two contract versions, direction-aware, with a stable rule id and severity per finding.
- `changelog` — Render the changes between two contract versions as a human changelog.
- `coverage` — Report which operations a contract declares, as a coverage baseline.
- `rules` — List every breaking-change rule with its id, severity and rationale.
- `plugins` — List the contract formats this installation can read.

Read-only on purpose: nothing in that subset writes a file, opens a socket or
runs another process.

### What not to do

- Do not hand-edit a generated document. `docs/rule-catalog.md`,
  `docs/check-rules.md` and the rest are produced by `scripts/generate_*.py`
  and CI fails when a committed copy disagrees with the code.
- Do not state a count in prose without deriving it. This project binds every
  such number to a test.
- Do not report that a check passed when it did not run. A target that could
  not be reached establishes nothing, and the tool distinguishes the two.
